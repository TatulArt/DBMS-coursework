# DBMS-coursework

Учебная СУБД на C++17 с SQL-подобным языком запросов и дисковым хранилищем.
Курсовая работа по системному программированию, **вариант 2: индекс на основе
B+ дерева**.

Данные хранятся в файлах постранично, индексируемые колонки обслуживаются
B+ деревом, а результат выборки печатается массивом JSON-объектов.

## Сборка и запуск

```bash
cmake -S . -B build
cmake --build build -j
```

```bash
./build/src/dbms_cli                 # интерактивный режим
./build/src/dbms_cli script.sql      # пакетный режим: выполнить файл сценария
```

Тесты:

```bash
cd build && ctest -j8
```

**Требования:** CMake ≥ 3.14, компилятор с поддержкой C++17, Flex и **Bison 3.0
или новее**. GoogleTest и nlohmann/json подтягиваются автоматически через
FetchContent.

> Грамматика использует `%language` и `api.value.type variant` — возможности
> Bison 3. В macOS штатно установлен Bison 2.3, поэтому корневой `CMakeLists.txt`
> сам находит версию из Homebrew (`brew install bison`). В Linux и devcontainer
> достаточно системного пакета.

## Язык запросов

Команды могут занимать несколько строк и завершаются `;`. Ключевые слова
регистронезависимы, но смешение регистров внутри одного слова запрещено
(`CrEaTe` отклоняется). Строковые литералы — в двойных кавычках.

### Работа с базами и схемами

```sql
CREATE DATABASE shop;
USE shop;
DROP DATABASE shop;

CREATE TABLE users (id INT INDEXED, name STRING NOT_NULL, dept STRING DEFAULT "общий");
DROP TABLE users;
```

Модификаторы колонок:

| Модификатор | Смысл |
|---|---|
| `INDEXED` | значение уникально и не может быть `NULL`; по колонке строится B+ индекс |
| `NOT_NULL` | запрет пустого значения (по умолчанию колонки nullable) |
| `DEFAULT <value>` | значение, подставляемое при `INSERT`, если колонка не указана |

### Манипулирование данными

```sql
INSERT INTO users (id, name) VALUE (1, "Alice"), (2, "Bob");
UPDATE users SET name = "Alice Smith" WHERE id == 1;
DELETE FROM users WHERE id == 2;

SELECT * FROM users;
SELECT name AS who, dept FROM users WHERE id == 1;
```

### Условия выборки

Сравнения `==`, `!=`, `<`, `>`, `<=`, `>=`; строки сравниваются
лексикографически.

```sql
SELECT * FROM users WHERE age BETWEEN 18 AND 65;   -- интервал [18, 65)
SELECT * FROM users WHERE name LIKE "Al.*";        -- регулярное выражение
SELECT * FROM users WHERE (age > 30 AND dept == "it") OR id == 1;
SELECT COUNT(*), SUM(salary), AVG(salary) FROM users;
```

Сравнение значений разных типов — семантическая ошибка, а не «ложь»: запрос
вернёт понятное сообщение вместо тихо пустого результата.

## Архитектура

```
main.cpp  →  DBMSEngine  →  SqlParser → AST  →  Executor  →  Database → Table
                                                                ↓         ↓
                                                        IndexManager   RecordManager
                                                             ↓              ↓
                                                         BPlusTree      PageManager
```

| Каталог | Назначение |
|---|---|
| `src/parser` | Лексер (Flex) и грамматика (Bison), узлы AST |
| `src/engine` | `DBMSEngine` — координатор, `Executor` — выполнение запросов, `Database`/`Table` — схемы и данные |
| `src/index` | `BPlusTree` (шаблон по типу ключа), `IndexManager` — каталог индексов, `TableIndexer` — связь индексов со страницами данных |
| `src/storage` | `PageManager` (файл как массив страниц по 4 КБ, список свободных страниц), `RecordManager` (slotted pages, цепочка страниц кучи), `Serializer` |
| `src/catalog` | Системный каталог |
| `tests` | Тесты GoogleTest |

### Раскладка файла таблицы

Каждая таблица — отдельный файл `data/<база>/<таблица>.dat`, разбитый на
страницы по 4 КБ:

| Страница | Содержимое |
|---|---|
| 0 | Заголовок базы: сигнатура, голова цепочки страниц кучи, первая страница каталога индексов, голова списка свободных страниц |
| прочие | Страницы кучи (slotted pages), узлы B+ деревьев, страницы каталога индексов |

* **Куча таблицы — односвязная цепочка страниц.** Заголовок slotted-страницы
  хранит `next_page_id`, а голова цепочки лежит в заголовке базы, поэтому
  объём таблицы ограничен только размером файла. Вставка сперва пробует
  страницу, куда клали прошлую запись, затем ищет свободное место по всей
  цепочке и лишь потом выделяет новую страницу.
* **Место удалённых записей возвращается в оборот.** `delete_record` помечает
  слот пустым, а при нехватке непрерывного места `insert_record` уплотняет
  страницу, сдвигая живые записи. Номера слотов при уплотнении сохраняются,
  поэтому `RecordId`, записанные в B+ деревьях, остаются валидными.
* **Свободные страницы переиспользуются.** Страницы, освободившиеся при слиянии
  узлов дерева, схлопывании корня или `DROP INDEX`, попадают в односвязный
  список свободных страниц; следующий `allocate_page()` берёт страницу оттуда,
  вместо того чтобы наращивать файл.

Записи никогда не пишутся на нулевую страницу: её первые байты — заголовок
базы, и slotted-заголовок затирал бы сигнатуру. Файлы таблиц, созданные
версией без этого заголовка, новым кодом не читаются — при обращении к такой
таблице СУБД сообщает, что файл нужно удалить и создать таблицу заново.

### Подсистема индексации

B+ дерево целиком лежит на диске: узел — одна страница 4 КБ. Дерево шаблонное
по типу ключа и инстанцируется дважды:

| Псевдоним | Ключ | Для колонок | Ключей в листе / узле |
|---|---|---|---|
| `BPlusTree` | `int32_t` (4 Б) | `INT` | 340 / 509 |
| `StringBPlusTree` | `StringKey` (128 Б) | `STRING` | 30 / 30 |

* **Вместимость** вычисляется из `PAGE_SIZE` и `sizeof(KeyT)`, а не задаётся
  константой. `static_assert` проверяет выравнивание массивов внутри страницы
  и то, что слияние двух недозаполненных узлов помещается в одну страницу.
* **Листья связаны в односвязный список**, поэтому диапазонный поиск — это один
  спуск по дереву плюс линейный проход по листьям.
* **Значение листа — `RecordId {page_id, slot_id}`**, то есть физический адрес
  записи: индекс ссылается на данные и не хранит их копий.
* **Ключи уникальны** — это и есть семантика модификатора `INDEXED`.
* **`StringKey`** — строка фиксированной длины (до 126 байт) со сравнением через
  `memcmp`, что даёт тот же порядок, что и `std::string`. Значения длиннее лимита
  отклоняются явной ошибкой, а не обрезаются: обрезание сделало бы разные строки
  одинаковыми ключами и сломало бы проверку уникальности.

Балансировка при удалении реализована полностью: при недозаполнении узла
сначала пробуется заимствование у соседа, затем слияние с рекурсивным подъёмом
к корню и понижением высоты дерева.

`IndexManager` хранит каталог индексов в цепочке страниц (ссылка лежит в
метаданных БД), поэтому индексы переживают перезапуск. Каждое дерево сообщает
каталогу о смене корня, благодаря чему в одном файле живёт произвольное число
индексов.
