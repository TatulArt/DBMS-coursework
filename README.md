# DBMS-coursework

Учебная СУБД на C++17. Вариант 2: индекс на основе **B+ дерева**.

## Сборка и запуск

```bash
cmake -S . -B build
cmake --build build -j
./build/src/dbms_cli      # демонстрация подсистемы индексации
cd build && ctest          # тесты
```

Требуются CMake ≥ 3.14, компилятор с C++17, Flex и Bison.
GoogleTest и nlohmann/json подтягиваются автоматически через FetchContent.

## Структура проекта

| Каталог | Назначение |
|---|---|
| `src/storage` | Страничное хранилище: `PageManager` (файл как массив страниц по 4 КБ), `RecordManager` (slotted pages), `Serializer` |
| `src/index`   | Подсистема индексации: `BPlusTree`, `IndexManager`, `TableIndexer` |
| `src/parser`  | Лексер и грамматика SQL-подобного языка (заготовка) |
| `tests`       | Тесты GoogleTest |

## Подсистема индексации

### `BPlusTree` — само дерево

Классическое B+ дерево, целиком живущее на диске: узел = одна страница 4 КБ.
Дерево шаблонное по типу ключа (`BPlusTreeT<KeyT>`) и инстанцируется дважды:

| Псевдоним | Ключ | Для колонок | Ключей в листе / узле |
|---|---|---|---|
| `BPlusTree`       | `int32_t` (4 Б)   | `INT`    | 340 / 509 |
| `StringBPlusTree` | `StringKey` (128 Б) | `STRING` | 30 / 30 |

* **Раскладка страницы.** Заголовок `BPlusTreeHeader` — 16 байт (тип узла,
  число ключей, ссылки на родителя и на следующий лист). Дальше идут массив
  ключей и массив значений. Размеры заголовка и ключа кратны 4 байтам,
  поэтому массивы остаются выровненными; это проверяется `static_assert`.
* **Вместимость** вычисляется из `PAGE_SIZE` и `sizeof(KeyT)`, а не задаётся
  константой. `static_assert` также проверяет, что слияние двух
  недозаполненных узлов гарантированно помещается в одну страницу.
* **`StringKey`** — строка фиксированной длины (до 126 байт) со сравнением
  через `memcmp`, что даёт ровно тот же порядок, что и `std::string`.
  Значения длиннее лимита не индексируются, а отклоняются явной ошибкой:
  обрезание сделало бы разные строки одинаковыми ключами и сломало бы
  проверку уникальности `INDEXED`-колонки.
* **Листья связаны в односвязный список** (`next_page_id`) — это даёт
  диапазонный поиск за один спуск по дереву плюс линейный проход по листьям.
* **Значение листа — `RecordId {page_id, slot_id}`**, то есть физический адрес
  записи. Сами данные в индексе не дублируются (требование задания).
* **Ключи уникальны**: повторная вставка возвращает
  `UniqueConstraintViolation` — это и есть семантика модификатора `INDEXED`.

Операции: `insert`, `search`, `update`, `remove`, `scan_range`,
`scan_range_half_open` (семантика `BETWEEN` — интервал `[low, high)`),
итератор `begin()/lower_bound()/end()` и `validate()` для проверки
структурной целостности.

Балансировка при удалении реализована полностью: при недозаполнении узла
сначала пробуется заимствование элемента у соседа (redistribute), затем
слияние с соседом (coalesce) с рекурсивным подъёмом к корню и понижением
высоты дерева.

### `IndexManager` — каталог индексов

Хранит соответствие «имя индекса → таблица, колонка, тип ключа, корневая
страница».
Каталог сериализуется в цепочку страниц; ID первой страницы лежит в
`DatabaseMetadata::index_catalog_page_id` на 0-й странице файла, поэтому
индексы переживают перезапуск СУБД.

Каждое дерево получает callback на смену корня, и `IndexManager` сохраняет
новый `root_page_id` в своей записи каталога. Благодаря этому в одном файле
может жить произвольное число индексов.

Ключи в API передаются как `Value`, а каталог сам выбирает нужное дерево по
типу колонки, поэтому вызывающему коду не нужно знать про `int32_t` и
`StringKey`.

### `TableIndexer` — связь индексов с данными

Слой, ради которого писалась ветка `feature/bplus-tree-indexing`:

* `build_index` — сканирует страницы данных таблицы и строит по колонке
  B+ индекс (или перестраивает существующий);
* `create_indexes_for_table` — создаёт индексы для всех колонок с `INDEXED`;
* `insert_row` / `delete_row` — пишут в кучу и синхронно поддерживают
  все индексы таблицы, проверяя типы, `NOT_NULL` и уникальность;
* `select_equal` / `select_range` — выбирают способ выполнения запроса:
  если по колонке есть индекс, идут через дерево, иначе делают полный скан.
  Использованный способ возвращается в `SelectResult::method`.

## Известные ограничения

* Значения в индексируемой `STRING`-колонке ограничены 126 байтами
  (`StringKey::MAX_LENGTH`); более длинные отклоняются при вставке.
* Нет списка свободных страниц: страницы удалённых индексов и слитых узлов
  остаются занятыми в файле.
* Нет каталога таблиц: схема и список страниц данных (`TableSchema`)
  передаются вызывающей стороной. Это задача уровня парсера/исполнителя.
* `RecordManager::delete_record` помечает слот удалённым, но не уплотняет
  страницу.
